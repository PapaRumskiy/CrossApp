# CrossApp

Наскрізний навчальний проєкт із кросплатформного програмування, розроблений мовою C# на платформі .NET.

**Предметна область:** Замовлення.

**Основні сутності:** Customer, Product, Order, OrderLine.

**Призначення:** представлення та імпорт даних про товари, створення замовлень, керування їхнім станом, перевірка бізнес-правил і підрахунок загальної вартості.

Проєкт побудований із розділенням доменної логіки та консольного інтерфейсу.

## Технології

- C#
- .NET 8 / .NET 10
- Visual Studio Code
- System.Text.Json
- CSV / JSON
- Git
- Docker

### Core

Бібліотека, яка містить основну логіку програми:

- DTO для передавання даних.
- Доменні сутності та бізнес-правила.
- Імпортери CSV/JSON.
- Перевірку коректності даних.
- Інформацію про середовище виконання.

### Cli

Консольний застосунок, який забезпечує:

- Отримання аргументів командного рядка.
- Вибір формату імпорту.
- Виведення завантажених даних.
- Виведення помилок і статистики.
- Демонстрацію роботи доменної моделі.

Залежність між проєктами:

```text
Cli → Core
```

Для підключення Core використовується `ProjectReference`.

## Представлення даних

Для опису даних використовуються record-типи.

### ProductDto

Представляє товар:

- `Id` — ідентифікатор.
- `Name` — назва.
- `Price` — ціна.

### WarehouseDto

Представляє склад:

- `Id` — ідентифікатор.
- `Name` — назва.

### ImportResult

Узагальнений тип `ImportResult<T>`, що містить:

- `Items` — успішно імпортовані записи.
- `Errors` — повідомлення про некоректні записи.

Це дозволяє продовжувати обробку файлу навіть за наявності пошкоджених рядків.

## Імпорт CSV та JSON

Реалізовано імпорт даних із файлів CSV та JSON.

### CSV

Використовується роздільник `;`.

Приклад:

```csv
id;name;price
P-001;Laptop;35000.50
P-002;Keyboard;2500.00
P-003;Mouse;800.99
```

Для аналізу рядків застосовуються:

- Pattern matching.
- Switch expressions.
- Property patterns.
- List patterns.
- Guard conditions (`when`).
- `decimal.TryParse`.
- `CultureInfo.InvariantCulture`.

Некоректні записи пропускаються із зазначенням номера рядка та причини помилки.

### JSON

Імпорт реалізований за допомогою `System.Text.Json`.

Для десеріалізації використовується `JsonSerializer.Deserialize`.

Параметр `PropertyNameCaseInsensitive` дозволяє зіставляти назви JSON-властивостей незалежно від регістру.

### Змішаний CSV

Підтримується імпорт різних типів записів:

- `P` — Product.
- `W` — Warehouse.

Приклад:

```csv
type;id;name;price
P;P-201;Laptop;35000.50
W;W-001;Main Warehouse;
P;P-202;Keyboard;2500.00
```

Тип запису визначається за допомогою pattern matching.

### Статистика імпорту

Після завантаження виводиться:

- Загальна кількість записів.
- Кількість прийнятих записів.
- Кількість пропущених записів.
- Відсоток помилок.
- Причини пропуску некоректних рядків.

## Доменна модель

Для реалізації бізнес-правил створено каталог `Core/Domain`.

### Order

Головна сутність, яка представляє замовлення.

Властивості:

- `Id` — ідентифікатор замовлення.
- `CustomerId` — ідентифікатор клієнта.
- `Status` — поточний стан.
- `Lines` — список позицій.
- `Total` — загальна вартість.

Основні методи:

- `Create()` — створення замовлення.
- `AddLine()` — додавання товару.
- `Confirm()` — підтвердження замовлення.
- `Cancel()` — скасування замовлення.
- `ToDto()` — перетворення в DTO.
- `FromDto()` — відновлення з DTO.

### OrderLine

Представляє окрему позицію замовлення.

Властивості:

- `ProductId` — ідентифікатор товару.
- `Name` — назва.
- `Price` — ціна за одиницю.
- `Quantity` — кількість.
- `Total` — загальна вартість позиції.

## Інваріанти

Доменна модель забезпечує дотримання бізнес-правил протягом усього життєвого циклу об'єктів.

| Інваріант | Виняток |
|---|---|
| Id замовлення обов'язковий | ArgumentException |
| CustomerId обов'язковий | ArgumentException |
| ProductId обов'язковий | ArgumentException |
| Назва товару обов'язкова | ArgumentException |
| Ціна товару не може бути від'ємною | ArgumentOutOfRangeException |
| Кількість товару повинна бути більшою за нуль | ArgumentOutOfRangeException |
| Порожнє замовлення не можна підтвердити | DomainException |
| Не можна додавати позиції до підтвердженого замовлення | DomainException |
| Не можна повторно підтверджувати замовлення | DomainException |
| Підтверджене замовлення не можна скасувати | DomainException |
| Повторне скасування заборонене | DomainException |

Усі перевірки виконуються перед зміною стану об'єкта.

Якщо операція порушує інваріант, генерується відповідний виняток зі зрозумілим повідомленням.

## Інкапсуляція

У доменній моделі використовується інкапсуляція:

- Критичні властивості не мають публічних сеттерів.
- Конструктори сутностей приватні.
- Створення виконується через фабричні методи `Create()`.
- Внутрішня колекція позицій захищена від зовнішніх змін.
- Стан замовлення змінюється лише через бізнес-методи.

Це запобігає створенню та зміні об'єктів із порушенням бізнес-правил.

## Статуси замовлення

Використовується перелічення `OrderStatus`:

```csharp
public enum OrderStatus
{
    Draft,
    Confirmed,
    Cancelled
}
```

Можливі переходи:

```text
Draft → Confirmed
Draft → Cancelled
```

Підтверджене або скасоване замовлення не можна повторно змінити через реалізовані методи переходів стану.

Для перевірки переходів використовується `switch expression`.

## DTO та доменні сутності

DTO використовуються для передавання й зберігання даних.

Доменні сутності відповідають за бізнес-логіку, інкапсуляцію та контроль стану.

Метод `ToDto()` перетворює сутність у DTO.

Метод `FromDto()` відновлює сутність, повторно перевіряючи інваріанти.

Файлове сховище використовує цей механізм для запису та завантаження агрегатів замовлень.

## Сервісний шар і сховища

`IOrderStore` визначає операції `List`, `GetById`, `Add`, `Update` і `Remove` для замовлення разом із позиціями. Пошук за відсутнім Id повертає `null`. Сховища порівнюють Id замовлень без урахування регістру, відхиляють дублікати та повертають окремі знімки. Щоб зберегти змінений агрегат, потрібно викликати `Update`.

- `InMemoryOrderStore` зберігає DTO у словнику протягом життя процесу. Демонстрація завантажує початкові замовлення з `SampleData`. Набір повертає нові екземпляри клієнтів і замовлень із фіксованими Id, цінами та статусами.
- `FileOrderStore` читає `data/orders.json` при першій операції та кешує дані в пам’яті. Відсутній або порожній файл означає порожнє сховище. Некоректний JSON, дублікати та DTO, які порушують інваріанти, дають помилку з шляхом до файлу. Запис створює каталог за потреби та замінює файл через тимчасовий файл у тому самому каталозі. Сума обчислюється з відновлених позицій. Файл розрахований на одного власника запису.
- `CachingOrderStore` кешує пошук за Id, включно з відсутніми записами. Після запису або видалення він скидає відповідний запис кешу. Усі зміни надходять через декоратор, а лічильник влучань показує, скільки пошуків обійшли внутрішнє сховище.
- `OrderService` приймає `IOrderStore` у конструкторі, викликає доменні методи й застосовує ліміт у п’ять активних замовлень на клієнта. Перевантаження `Find(Func<Order, bool>)` приймає лямбди для пошуку за статусом, клієнтом і сумою.

`Program.cs` виконує ручне впровадження залежностей. Він отримує сховище з `StoreFactory.Create(args)`, обгортає його в декоратор і передає в `OrderService`. Прямий вибір у `Program.cs` робить створення об’єктів видимим в одному місці й підходить для короткої умови. Фабрика тримає вибір реалізації, шлях та початкові дані разом і дає змогу перевіряти цей вибір окремо. За це додається один рівень виклику.

## Доменні події

`OrderService.Changed` має тип `EventHandler<OrderChangedEventArgs>`. Сервіс спочатку виконує доменну операцію й зберігає її результат, потім синхронно сповіщає підписників. Види подій охоплюють `Created`, `LineAdded`, `Confirmed`, `Cancelled` і `Removed`. Дані події містять Id замовлення та клієнта, статус, кількість позицій, суму й час у UTC. Для `Removed` ці поля описують останній стан видаленого замовлення. Відхилена операція, невдалий запис або видалення відсутнього замовлення не породжують сповіщення.

`+=` додає обробник до списку підписників, а `-=` прибирає збережений делегат. У `--lab06` іменований обробник пише в консоль і файл, а лямбда `(_, _) => changes++` захоплює локальну змінну `changes`. Після відписки логера лямбда залишається у списку викликів і отримує наступну подію. Нова лямбда в правій частині `-=` не видалить початкову підписку.

- `Action<T>` виконує дію без значення, що повертається. У CSV-імпортері `Action<string>` отримує причину пропуску рядка.
- `Func<T, TResult>` повертає значення. `Find(Func<Order, bool>)` використовує результат `bool`, щоб вирішити, чи включати замовлення до результату пошуку.
- `event` сповіщає про факт, який уже відбувся. Власник події викликає її, а зовнішній код додає та видаляє обробники.

### Підписка та впровадження `INotificationSink`

| Властивість | `INotificationSink` | `Changed` |
|---|---|---|
| Залежності | Необов’язковий sink передається через конструктор. Core знає інтерфейс, а CLI обирає реалізацію. | Підписники знають про сервіс і тип аргументів події. Сервіс знає лише делегат. |
| Підписники та гнучкість | Один sink на екземпляр сервісу, обраний під час ручного DI. | Будь-яка кількість обробників, які можна підписувати й відписувати під час роботи. |
| Тестування | Тестовий sink накопичує аргументи, передані до `Notify`. | Тестовий обробник накопичує аргументи або рахує виклики та перевіряє відписку. |
| Обробка помилок | Виняток sink повертається викликачеві після збереження замовлення й публікації події. | Синхронний виняток обробника повертається викликачеві після збереження. Він перериває виклик решти обробників і подальше звернення до sink. |

`ConsoleSink` і `FileSink` розміщені в CLI. Сценарій підписки додає рядки до `logs/app.log`. Окремий сценарій із `FileSink` через DI пише до `logs/sink.log`, тому обидва механізми не записують одну подію двічі. Один рядок журналу містить час UTC у форматі ISO 8601, операцію, Id замовлення, клієнта, статус, кількість позицій і суму з десятковою крапкою. Каталог створюється автоматично, нові запуски дописують записи.

### Callback під час імпорту CSV

`ProductCsvImporter.Load(path, onSkipped)` передає повідомлення до `Action<string>?` після додавання його до `ImportResult.Errors` і продовжує обробку наступних рядків. У `--lab06` CLI передає лямбду, яка виводить повідомлення та накопичує їх для звірки. Виклик `Load(path)` працює без callback. Якщо код самого callback викидає виняток, він передається викликачеві.

### Асинхронні обробники та `async void`

Стандартний делегат `EventHandler<T>` повертає `void`. Якщо його обробнику потрібен `await`, підпис може вимагати `async void`. Видавець події одразу продовжує роботу і не має об’єкта `Task`, за яким можна дочекатися завершення або перевірити результат у тесті. Винятки з `async void` передаються до поточного контексту синхронізації або обробляються середовищем як необроблені. Звичайний `try/catch` навколо виклику делегата їх не перехоплює.

Звичайні асинхронні методи повертають `Task` або `Task<T>`, щоб викликач міг застосувати `await`, обробити виняток і перевірити завершення в тесті. У лабораторній №8 цей підхід потрібен для асинхронних операцій із введенням і виведенням. Якщо асинхронний обробник потрібен на межі інтерфейсу, він може викликати метод із `Task` та обробити виняток усередині обробника. Бізнес-сервіс лабораторної №6 синхронний.

## LINQ-звіти про замовлення

`Core/Reports/ReportService` приймає `IEnumerable<Order>` і, для звіту за клієнтами, `IEnumerable<Customer>`. Він виконує LINQ to Objects та повертає DTO. Результати списків матеріалізуються в масиви. Для загальної статистики джерело читається один раз у масив сум, на якому обчислюються агрегати.

| Команда | Результат | LINQ-оператори |
|---|---|---|
| `report-top` | П’ять клієнтів з найбільшою сумою замовлень | `GroupBy`, `Sum`, `Select`, `TopBy` |
| `report-high [поріг]` | Усі замовлення із сумою строго понад поріг. Типовий поріг — 2000. | `Where`, `OrderByDescending`, `ThenBy`, `Select` |
| `report-groups` | Кількість і сума за кожним наявним статусом | `GroupBy`, `OrderBy`, `Count`, `Sum`, `Select` |
| `report-sum` | Кількість, сума, середній чек і максимальна сума. Для порожнього джерела всі показники дорівнюють нулю. | `Select`, `Sum`, `Average`, `Max` |
| `report-customers` | Імена, кількість і сума замовлень усіх відомих клієнтів | `GroupJoin`, `Count`, `Sum`, `OrderBy` |
| `report-orders [N]` | Топ-N замовлень за сумою. Типове N — 5. | `Select`, `TopBy` |

Звіти враховують усі статуси. Типове джерело містить 18 відтворюваних замовлень і 7 клієнтів із `SampleData`. Опція `--file` перемикає звіти на поточні замовлення з `data/orders.json`. У `report-customers --file` довідником клієнтів залишається `SampleData.CreateCustomers()`, тому в цьому звіті відображаються лише клієнти з довідника. `GroupJoin` зберігає клієнтів із порожньою групою, як-от Софію Лисенко (`C-507`) з кількістю 0 та сумою 0,00. Id групуються, зіставляються й сортуються з порядковим порівнянням.

### `TopBy` і два синтаксиси LINQ

`TopBy<T>` використовується в рейтингу клієнтів і топі замовлень. Він приймає числовий селектор `decimal`, кількість і селектор Id. Реалізація поєднує `OrderByDescending`, `ThenBy` і `Take`. Рівні суми сортуються за Id, а повністю рівні ключі зберігають порядок джерела. Для N = 0 результат порожній без перебирання джерела, від’ємне N дає виняток, а N понад довжину повертає всі елементи в порядку рейтингу.

`report-groups` порівнює за значеннями DTO дві версії звіту, написані через `GroupBy(...).OrderBy(...).Select(...)` і `from … group … by … into … orderby … select …`. У тестових даних усі три групи збігаються за порядком, кількістю та сумою. Методний синтаксис прямо показує ланцюжок операторів і зручно поєднується з `TopBy`, `Take` та агрегатами. Синтаксис запиту читабельний для іменованих груп, з’єднань і проміжних змінних, а оператори на кшталт `Take` усе одно додаються викликами методів.

### Відкладене виконання і знімок

`report-deferred` зберігає результат `Where` як запит до локального `List<Order>`. Перший `Count()` дає 1, після додавання відповідного замовлення повторний `Count()` дає 2. Після `ToList()` і очищення джерела запит дає 0, а матеріалізований список усе ще містить 2 елементи. `ToList()` фіксує склад списку під час виклику, а елементи залишаються посиланнями. DTO звітів окремо фіксують значення полів.

### Вимірювання Stopwatch

`report-benchmark` створює 100 000 відтворюваних записів до початку вимірювання. Обидва варіанти фільтрують за статусом і сумою, проєктують суми й обчислюють однаковий результат `79 980 000,00`. Після прогріву виконується 7 вимірювань на варіант зі зміною порядку запуску. Введення й виведення відбуваються поза вимірюваною ділянкою.

Фактичний запуск у Release з .NET SDK 10.0.401

| Варіант | Медіана часу, мс | Медіана виділених байтів |
|---|---:|---:|
| `Where → Select → Sum` | 2,351 | 112 |
| `Where → ToList → Select → Sum` | 3,934 | 213 464 |

Проміжний список у цьому вимірюванні додає виділення пам’яті та окремий прохід по відібраних записах. Лічильник показує виділені байти потоку під час запиту. Час залежить від середовища та навантаження. Матеріалізація має сенс, коли потрібен знімок або багаторазове читання результату.

## Асинхронний імпорт замовлень

`--lab08` передає `CancellationToken` від CLI через `OrderService` до `JsonOrderImporter`. `IOrderImporter.LoadAsync` відкриває асинхронний `FileStream`, викликає `JsonSerializer.DeserializeAsync` для масиву `OrderDto` і перевіряє кожен запис через `Order.FromDto`. Вхідним прикладом є `data/orders-import.json`. Усі записи пакетного імпорту валідуються до першого збереження.

`IStreamingOrderImporter.StreamAsync` використовує `DeserializeAsyncEnumerable`, `await foreach` і `[EnumeratorCancellation]`. Сервіс обробляє записи у міру надходження. Парсер утримує буфер і поточні записи, а пам’ять сховища зростає відповідно до його реалізації. У разі помилки в пізнішому записі потоковий імпорт може вже зберегти попередні записи.

Обидва режими відновлюють готові агрегати, перевіряють їхні доменні інваріанти та пропускають наявні Id без урахування регістру. Ліміт активних замовлень залишається правилом реєстрації нового замовлення в `CreateOrder`. Сервіс зберігає імпортований запис через `IOrderStore.Add` і після повернення цього методу публікує одну подію `Created`. Записи сховища залишаються синхронними. Скасування діє кооперативно перед читанням, у JSON-десеріалізації, при відновленні позицій і між записами. Уже збережені зміни можна залишити в сховищі та без дублікатів повторити імпорт.

`DomainException` описує порушення бізнес-правил, наприклад повторне підтвердження. Прямі виклики з невалідною ціною або кількістю дають `ArgumentException` чи `ArgumentOutOfRangeException`. Під час відновлення запису імпортер додає його номер з одиниці у `DomainException` та зберігає причину в `InnerException`. Відсутній файл, помилка файлової системи, некоректний JSON і скасування мають окремі типи винятків.

CLI пов’язує токени користувача і таймауту через `CancellationTokenSource.CreateLinkedTokenSource`. `Ctrl+C` встановлює токен користувача, а `--cancel-after-ms N` запускає таймер. Тимчасовий обробник `Console.CancelKeyPress` відписується в `finally`. Код виходу ручного скасування або `--cancel-before` — 130, таймауту — 124. `--stream --delay-ms N` додає контрольовану паузу між записами для демонстрації.

`IProgress<int>` у пакетному режимі передає відсоток оброблених записів. Запис, пропущений через дублікат, теж оброблений. Три записи дають 0%, 33%, 66% і 100%, а порожній масив дає 0% і 100%. Потоковий режим передає кількість оброблених записів, бо загальний розмір невідомий. Після скасування виводиться повідомлення, а лічильник зберігає останнє досягнуте значення.

### Unit-тести та покриття

`tests/Core.Tests` використовує xUnit і .NET 10 та має посилання на Core. Сценарії використовують нові екземпляри сховища й фіксовані дані. Тести файлового імпортера пишуть власний JSON у тимчасовий каталог і видаляють його у `finally`. Тест таймауту запускає таймер лише після сигналу від fake-імпортера, який очікує на скасування.

```powershell
dotnet test
dotnet test --collect:"XPlat Code Coverage"
```

Збір виконує `coverlet.collector`. Файл із результатами `coverage.cobertura.xml` створюється в `tests/Core.Tests/TestResults`. Фактичний запуск дав 33 пройдені тести, 0 невдалих і 0 пропущених. Пакет Core має **51,63% покриття рядків** (459 із 889) і **43,62% покриття гілок** (106 із 243).

Тести зосереджені на інваріантах, подіях, звітах і новому імпорті. `FileOrderStore`, старі CSV/JSON-імпортери та LINQ-бенчмарк перевірено окремими запусками CLI, які не входять до звіту Coverlet. Наступні корисні сценарії для автоматизації — відмови реального файлового сховища, крайні випадки старих імпортерів та дані середовища.

## Publish

### Self-contained

Self-contained версія містить .NET Runtime і не потребує його окремого встановлення на цільовій системі.

```powershell
dotnet publish src/Cli -c Release -r win-x64 --self-contained true -o publish/win-x64-self-contained
```

### Framework-dependent

Framework-dependent версія потребує встановленого .NET Runtime відповідної версії.

```powershell
dotnet publish src/Cli -c Release -r win-x64 --self-contained false -o publish/win-x64-framework-dependent
```

Self-contained публікація зазвичай займає більше дискового простору, оскільки містить компоненти середовища виконання.

## Перевірка опублікованих застосунків

Self-contained:

```powershell
.\publish\win-x64-self-contained\Cli.exe --lab04
```

Framework-dependent:

```powershell
dotnet publish/win-x64-framework-dependent/Cli.dll --lab04
```

Параметр `--lab04` запускає демонстрацію доменної моделі та читає `data/sample.csv` від поточного робочого каталогу. Запускайте опублікований застосунок з кореня репозиторію або покладіть зразок у `data` відносно каталогу запуску.
